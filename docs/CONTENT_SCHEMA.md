# Content & Data Schema

The types live in `src/types/content.ts`. `scripts/validate-content.ts` validates all JSON in `content/` against them (zod).

## Curriculum (`content/curriculum.json`, version 2)
Generated by `scripts/build_curriculum.py`; **do not hand-edit the JSON**. The types are in `src/types/content.ts` (mirroring `docs/curriculum-v2.types.ts`); `scripts/curriculum-schema.ts` validates them.

Shape in short:
- `Curriculum { version: 2, defaultStartDate, totalPlanDays: 90, mockSpec, practicalTasks[16], weeks[13] }`. Week 13 has 6 days, the others 7.
- `Week { week, title, goal, concepts, visuals, templates, days, pool, problemCount, oldTopicCount }`. `pool` holds spare problems for mock Program 1 and free practice; pool problems never count toward day status.
- `PlanDay { day, planDay (1–90), kind, mock | null, learn | null, problems, fallback | null, timedMinutes | null, codingNote | null }`.
  - `kind`: `new-topic | topic | python-fluency | old-topics | timed | redo | wrap-up`.
  - Curriculum v3 has no `mock` on a day. `reviewSlots` is 2 on every day from plan day 5 except the wrap-up, and 0 on plan days 1–4. The top-level `mocks` list (26 entries with `suggestedAfterWeek`) replaces the old per-day mock.
  - A day's items are its `learn` item (if non-null) plus `problems`. The wrap-up day has neither and gets one manual item (`w13-d6:wrapup`). A `fallback` is never an item: it is shown only when the redo queue is empty and never affects day status or the catch-up queue.
- `Problem { id, platform: "LeetCode" | "HackerRank", lcNumber?, title, difficulty, url, role: "core" | "old-topic" | "fallback" | "pool", fromWeek? }`. Ids: `w03-d2-p1`, `w03-d7-fb`, `w03-pool-04`. **`fromWeek` (old-topic only) must never be shown** before the problem has been attempted.
- Item ids: problem id, `w03-d1:learn` (new-topic days only), `w03-d6:review-1` / `:review-2` (review slots; the problem is in the `dayDraws` table), `w13-d6:wrapup`, and redo slots `w03-x1:s1` / `:s2` on **extension days only**.

See `scripts/curriculum-schema.ts` for every validated rule (90 days, mock numbering and python-theme rotation, unique ids and URLs, `fromWeek` earlier than the week, a `redo` day has a `fallback`, learn items on mock and new-topic days, per-week counts).

## Questions (`content/questions/week-NN.json`)
```ts
export type QuestionType = "pattern" | "complexity" | "output" | "bug" | "approach" | "concept";

export interface Question {
  id: string;            // "w01-q07" (week file) or "t01-q07" (Python-theme file) — stable, never reuse
  week: number;
  type: QuestionType;
  pattern: string;       // e.g. "Sliding Window", used by the dashboard
  difficulty: "medium" | "hard"; // interview level
  prompt: string;        // markdown allowed
  code?: string;         // Python 3.11
  options: string[];     // 4 options
  answer: number;        // index into options
  explanation: string;   // why, incl. time/space when relevant
  complexity?: { time: string; space: string };
  visual?: { component: string; props: Record<string, unknown> }; // optional diagram
  tags?: string[];
  theme?: number;        // 1–15, required on Python-theme questions (ids "t01-q07")
}

export interface QuestionFile { week: number; theme?: number; questions: Question[]; drill?: DrillPrompt[]; }

export interface DrillPrompt {
  id: string;            // "w03-dr04"
  week: number;
  description: string;   // 1–3 sentence problem statement, no title
  answer: string;        // pattern name
  distractors: string[]; // 5 other pattern names
}
```

Rules:
- `content/questions/week-NN.json`: ≥ 20 questions, `week` = NN, ids `wNN-qXX`. No minimum per type.
- `content/questions/python-theme-NN.json` (NN = 1–15): ≥ 8 questions, `"theme": NN` on the file and on every question, ids `tNN-qXX`, `week` = the week of the theme's first mock. Question ids are unique across all files.
- `output` questions: `code` must print exactly one line; the correct option must equal that line. Checked by `scripts/check_outputs.py`.
- Distractors must be plausible (common mistakes), never joke answers.
- `drill` prompts are optional (the drill is being replaced by mocks).

### Example
```json
{
  "id": "w03-q12",
  "week": 3,
  "type": "complexity",
  "pattern": "Sliding Window",
  "difficulty": "medium",
  "prompt": "What is the time complexity of this function for a string of length n?",
  "code": "def longest(s):\n    seen, l, best = set(), 0, 0\n    for r, ch in enumerate(s):\n        while ch in seen:\n            seen.remove(s[l]); l += 1\n        seen.add(ch)\n        best = max(best, r - l + 1)\n    return best",
  "options": ["O(n)", "O(n²)", "O(n log n)", "O(n · k) where k = alphabet size"],
  "answer": 0,
  "explanation": "The while loop looks nested, but l only moves forward, so each index is added and removed at most once: O(n) total. Space O(min(n, alphabet)).",
  "complexity": { "time": "O(n)", "space": "O(min(n, Σ))" }
}
```

## Practical tasks (`content/practical/pt-NN.json`)
`{ id, title, unlockWeek, intro, rules[], levels: [3 × { level 1–3, title, prompt, signature, sampleInput, expectedOutput, edgeCases[] }] }`. `id`, `title` and `unlockWeek` must match the entry in `curriculum.json` `practicalTasks`.

## Debug snippets (`content/mock-extras/debug.json`)
`{ snippets: [{ id "dbg-NN", title, topic, week, code (15–25 lines), bugLine (1-based, inside code), bug, fix, fixedCode, expected, actual, explanation }] }`. `actual` is what the buggy code outputs; `expected` what the fixed code outputs.

## Progress (Dexie / IndexedDB)
```ts
// Completions belong to plan items, not dates, so extensions can move dates safely.
export interface ItemCompletion {
  itemId: string;        // primary key: a problem id ("w03-d2-p1"), "w03-d2:learn", or an extension slot "w03-x1:s1"
  planDayId: string;     // "w03-d2" or extension day "w03-x1"
  completedOn: string;   // YYYY-MM-DD when actually done
  attemptId?: number;    // the ProblemAttempt that produced this completion (lets "untick" undo it)
}

export interface WeekExtension {
  id?: number;
  week: number;
  extraDays: number;     // 1–14 total per week (sum of all extensions for that week)
  reason?: string;
  createdOn: string;     // YYYY-MM-DD
}

// Computed in lib/schedule.ts, never stored:
export interface ScheduledDay {
  planDayId: string;     // "w03-d2" | "w03-x1"
  week: number;
  kind: "plan" | "extension";
  date: string;          // YYYY-MM-DD from startDate + preceding days + extensions
}

export interface ProblemAttempt {
  id?: number;
  problemId: string;
  date: string;
  outcome: "alone" | "hint" | "solution" | "failed";
  minutes: number;
  note?: string;
  isRedo: boolean;
}

export interface RedoTask {
  id?: number; problemId: string; dueOn: string;
  doneOn?: string;               // closed as completed (re-solved alone)
  attemptedOn?: string;          // closed as attempted (hint/solution): a fresh redo chain replaced it
  createdByAttemptId?: number;   // lets "untick" delete redos the attempt created
  closedByAttemptId?: number;    // lets "untick" reopen redos the attempt closed
}

export interface QuizAnswer {
  id?: number;
  questionId: string;
  correct: boolean;
  answeredAt: string;    // ISO timestamp
  mode: "weekly" | "review" | "targeted" | "drill";
  ms?: number;           // time to answer (drill)
}

export interface CardState { questionId: string; box: 1 | 2 | 3 | 4 | 5; dueOn: string; }

export interface RestDay { date: string; }

export interface MockSession {
  id?: number; date: string; problemIds: string[];
  checklist: Record<string, boolean[]>; rating: 1 | 2 | 3 | 4 | 5; notes?: string;
}

// Added in Dexie schema v2 (SPEC 3.13)
export interface CustomItem {
  id: string;            // "c-<uuid>"; used as itemId in completions and problemId in attempts/redos
  planDayId?: string;    // day it belongs to ("w03-d2" or "w03-x1"); omitted = journal-only "found" problem
  week: number;          // topic week, for filtering
  kind: "problem" | "task";
  platform?: string;     // "LeetCode" | other; problems only
  title: string;
  difficulty?: Difficulty; // problems only
  url?: string;
  createdOn: string;
}

export interface ItemMove {
  itemId: string;        // primary key: plan item id that was moved
  fromPlanDayId: string;
  toPlanDayId: string;   // same week or its extension days
  movedOn: string;
}

// Journal data for ANY problem (plan, custom or found). Added in Dexie v2 (SPEC 3.14)
export interface ProblemEntry {
  problemId: string;     // primary key: plan problem id, or a CustomItem id ("c-…")
  description?: string;  // markdown
  approach?: string;     // markdown
  code?: string;         // Python
  timeComplexity?: string;
  spaceComplexity?: string;
  insight?: string;      // key insight / what I missed
  comments?: string;
  confidence?: 1 | 2 | 3 | 4 | 5;
  tags: string[];        // pattern tags
  updatedOn: string;
}

export interface DayLog {
  planDayId: string;     // primary key
  notes: string;         // markdown
  minutes: number;
  links: string[];
  updatedOn: string;
}

export interface Settings {
  id: "settings"; startDate: string; theme: "light" | "dark" | "system";
  leetcodeUrl?: string; hackerrankUrl?: string; // https only; empty/missing/invalid -> defaults (https://leetcode.com/problemset/, https://www.hackerrank.com/dashboard)
}
```
Export/import = one JSON object with every table plus `schemaVersion`.

## Resources (`content/resources.json`, optional) and `TopicCheck` (Dexie v8)

Feeds the Content page's Data Structures, Patterns and Concepts tabs. While the file is absent each tab says "No topics yet". Validated by `scripts/resources-schema.ts` (the file is optional: validation passes when it is missing).

```ts
type TopicKind = "data-structure" | "pattern" | "concept";
interface ResourceLink { site: string; title: string; url: string }   // url is https
interface Topic {
  id: string;                 // unique across the whole file
  title: string;
  kind: TopicKind;
  structure?: string;         // required for "data-structure": groups topics, e.g. "Hash table (dict, set)"
  resources: ResourceLink[];  // at least 2
}
interface ResourcesFile {
  version: number; checkedOn: string; note: string;
  roadmap: { title: string; url: string };
  weeks: { week: number; title: string; neetcode: string; topics: Topic[] }[]; // week = a curriculum week, once each
}
// Dexie v8 table `topicChecks`, key topicId: a ticked topic. Exported/imported; v1-v7 exports import with it empty.
interface TopicCheck { topicId: string; checkedOn: string }
```

The Content page's Problems tab reads `curriculum.json` only (day problems, fallbacks, pools). Old-topic and pool problems never show the week or topic they came from.

## Data structures (`content/data-structures.json`, optional)

One entry per structure the Data Structures tab lists (16), including ones the plan does not teach. Validated by `scripts/data-structures-schema.ts`: names unique, https URLs, and every `structure` name used in `resources.json` must exist here.

```ts
interface StructureInfo {
  name: string;                        // matches the "structure" field in resources.json
  hackerrankSubdomain: string | null;  // "Open the <sub-domain> sub-domain on that page"; null = "No sub-domain: practise under Algorithms or the Interview Preparation Kit"
  inPlan: boolean;                     // false = shown with a "Beyond the plan" badge
  hackerrankUrl: string;               // https; the "Practise on HackerRank" button
}
interface DataStructuresFile { version: number; checkedOn: string; note: string; hackerrank: { title: string; url: string; dashboard: string }; structures: StructureInfo[] }
```

A structure is "taught" in a week when `resources.json` has a `data-structure` topic for it in that week. That decides the weeks shown on its card, the week selector filter, and the weeks whose plan problems its page lists. The HackerRank dashboard link on a structure page comes from Settings (`hackerrankUrl`), not from this file.

## Concepts: ids, `content/concept-links.json` (optional) and `ConceptCheck` (Dexie v9)

Every string in `curriculum.json` `weeks[].concepts` is a concept card with a **stable id built from week and 1-based position**: `w03-c2` is the 2nd concept of Week 3 (`src/lib/conceptIds.ts`). Ids never come from the text. **Only append concepts to the end of a week's list**: reordering or removing one moves the ids and breaks the links file and saved ticks. `src/lib/conceptIds.test.ts` (with `src/lib/fixtures/concept-ids.json`) fails if any of the 80 current ids changes its concept.

The `concept` topics of `resources.json` also show on the Concepts tab, as **"Core reading"** cards first in their week; they keep their topic id and their tick stays in `topicChecks`.

```ts
// content/concept-links.json (optional): 2-3 https links per concept, no duplicate URL within a concept; keys must exist in the curriculum.
interface ConceptLinksFile { version: number; concepts: Record<string /* "w03-c2" */, { site: string; title: string; url: string }[]> }
// Dexie v9 table `conceptChecks`, key conceptId: a ticked numbered concept. Exported/imported; v1-v8 exports import with it empty.
interface ConceptCheck { conceptId: string; checkedOn: string }
```

A concept with no entry (or no file) shows a quiet "Links coming" note. Validated by `scripts/concept-links-schema.ts`.
